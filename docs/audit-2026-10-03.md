## Scope and baseline

The audit covers runtime modules, parsers, lifecycle operations, installers,
packaging, CI gates, benchmarks, documentation and open GitHub work. Repository
documentation was read before implementation, using master commit
`3a96fc6db1caba331aeed1782562e108d28e0211` (4.9.2). The working branch starts at
`2fbdff5454e2a694a6c2d5fb49e9465b19151304`, the head of CPU batch-size PR #225.
The existing installation and its indexed corpus were not modified.

The baseline test run excluded the two Windows process/startup test modules
while investigating unsafe PID probes: 785 passed, 1 skipped, 5 deselected,
8 xfailed. This is a partial baseline, not an all-tests-passed claim.

## Confirmed defects and corrections

| Area | Observed failure | Correction / validation target |
| --- | --- | --- |
| Metrics | Every histogram observation remained in memory; labeled histogram names were malformed | Aggregate count/sum/buckets; bounded retention per series and valid exposition |
| Embeddings | Requested GPU provider determined batch size even after CPU fallback | Inspect actual session provider before choosing CPU/CUDA/DirectML batch |
| Lazy model loading | Concurrent first use could load more than one model | Synchronize initialization and publish only a validated session |
| Vector validation | Invalid rank, dimensions or non-finite values could reach storage | Validate every streamed embedding vector |
| FTS5 | Replaying chunk IDs duplicated rows; updates scanned text-table identities | Indexed identity mapping, idempotent upsert, transactional migration |
| FTS5 builder paths | A custom configured Chroma directory was ignored | Honor the configured path by default and use the conventional child path only for explicit CLI overrides |
| Chroma opening | Generic initialization errors could trigger deletion of the data directory | Preserve data and surface the cause |
| Incremental indexing | Parsed the corpus before checking unchanged metadata | Discover paths first, parse only selected documents |
| Forced indexing | Existing IDs could keep old vectors | Replace/upsert source chunks and verify with real ChromaDB |
| Rebuild publication | Failure after deleting the old collection made rollback invalid | Retain the old collection until replacement state is persisted |
| Concurrent publication | A query could retain the old Chroma handle while rebuild deleted it | Drain in-flight readers only at publication; staging inference keeps serving reads |
| Source versions | A source edited during inference could be recorded as already indexed | Carry the pre-parse file stat into metadata so the next scan detects the edit |
| Partial orphan pruning | One deletion failure prevented successful deletions from being persisted | Retain failed documents, count errors and persist successful removals |
| Retired collections | Failed post-commit deletion left old collections outside TTL cleanup | Include retired backups while preserving them when the primary collection is absent |
| Document mutations | Failed update/delete could discard maps or old content | Scoped rollback and coordinated mutation lifecycle |
| Source traversal | Symlinks could escape the corpus or form cycles | Containment and cycle checks; real filesystem tests |
| Query cache | Snippet changes could affect cached full content | Copy mutable result structure while sharing immutable strings |
| Cache invalidation race | A query reading old content could repopulate cache after a document update invalidated it | Fence both query-cache writes with an invalidation generation; real Chroma/FTS5 race regressions |
| Retrieval hydration | Keyword-only hits caused repeated storage reads | Batch hydration; preserve reranking candidate pool |
| Windows process checks | `os.kill(pid, 0)` was unsafe for this use on Windows | Non-signaling WinAPI liveness checks and a real child-process test |
| Single-instance race | Two stale-PID recoveries could both enter the guarded process | Hold a platform OS file lock on a stable sidecar; subprocess contention and abrupt-exit recovery tests |
| Optional Chroma metadata | A legal `None` metadata entry caused query scoring to fail | Normalize absent metadata in semantic, similar and category-filtered retrieval |
| Semantic-only search | First query allocated the BM25 corpus even with semantic weight 1.0 | Initialize BM25 only when lexical scoring is requested |
| Post-commit cleanup | A backup deletion error returned failure after a successful update and skipped cache invalidation | Report cleanup failures while preserving committed success; restoration failures still surface |
| MCP stdio | Global stdout mutation and diagnostic prints could corrupt protocol output | Explicit stderr diagnostics and real subprocess MCP tests |
| Relative paths | Child preflight could resolve the root twice | Pass resolved root and cwd; regression for issue #233 |
| Evaluation | Path substrings and separator differences could misidentify an expected source | Path-component matching and Windows/Unix regression cases |
| Installer configuration | Invalid JSON could be overwritten despite a preservation warning | Refuse invalid structures without changing bytes; atomic write-failure tests |
| Installer execution | Selected Python was ignored; dry-run created directories | Create venv with the selected executable; no-write dry-run verified on Windows |
| Distribution | Multilingual preset was absent from the wheel; bundled defaults drifted | Synchronize source/bundle and validate actual wheel initialization outside the checkout |
| Fresh checkout | A broad `data/` ignore rule hid the new bundled preset from Git | Explicitly version package resources; validate normal Git inclusion and initialization from a tracked-only archive |
| Public API gate | Optional parameters becoming required and positional-only defaults were missed | Compare call shape with adversarial compatibility fixtures; preserve the existing baseline |

Documentation now distinguishes source files from chunks, actual metrics from
unimplemented metrics, configuration defaults from historical plans, and handled
rollback from crash-proof atomicity. Model migrations use isolated data and
metadata so incompatible profiles do not overwrite an existing index.

## Real CPU and NVIDIA workload

Hardware: Windows 11 x64, NVIDIA RTX 3080 Ti, approximately 64 GiB system RAM.
Both final runs used the same isolated Python 3.12.7 interpreter, FastEmbed
0.8.1, ONNX Runtime GPU 1.26.0, ChromaDB 1.5.9, model, source hashes, two
inference threads and workload. CPU was explicitly selected for its run;
default micro-batches were 32 on CPU and 256 on CUDA.

Model: `BAAI/bge-small-en-v1.5`, 384 dimensions. ONNX SHA256:
`51f1bd0addd6e859e42c2c8021a5e5461385bb676a649f4b269aa445449f2431`.

`scripts/audit_retrieval.py` indexed seven public repository documents into a
temporary real ChromaDB collection and FTS5 database. It checked 149 initial
chunks, finite stored vectors, duplicate IDs, unchanged scans, editing one
Unicode-named file, deleting a source, forced reindex, concurrent reads and
reopening the persisted index. All those checks passed on both backends.

| Measurement | CPU | CUDA |
| --- | ---: | ---: |
| Initial indexing, including first model use | 13.655 s | 0.832 s |
| Unchanged scan, zero parser calls | 7.86 ms | 7.61 ms |
| Uncached query median, 36 requests | 11.13 ms | 6.10 ms |
| Uncached query p95, 36 requests | 13.91 ms | 7.44 ms |
| Cached query median | 0.033 ms | 0.028 ms |
| Sampled process peak RSS | 1,416,138,752 B | 989,638,656 B |
| Process RSS after closing test orchestrators | 236,273,664 B | 914,485,248 B |

RSS includes imported libraries and native allocations. CUDA retained more
process memory after teardown in this workload; a lower peak does not mean all
runtime memory was released. Sampling at 20 ms can miss shorter allocation
peaks. These are short local runs, not universal throughput or memory guarantees.
The cross-encoder was disabled to isolate indexing and hybrid retrieval.

Six English and six Portuguese questions used independently specified expected
source files. Both backends produced the same expected-source ranks:

| Language | Recall@5 | MRR@5 |
| --- | ---: | ---: |
| English | 1.000 | 0.875 |
| Portuguese | 1.000 | 0.792 |

This small documentation corpus does not establish general multilingual quality.
It measures whether one expected source appears among five returned chunks, not
all relevant documents or generated-answer correctness.

A separate offline application smoke exercised the real
`Xenova/ms-marco-MiniLM-L-6-v2` reranker with eight English/Portuguese candidates
and one query in each language. All 16 candidate scores were finite; each call
returned three scores in descending order and ranked the expected source first.
The first call, including load, took 141.9 ms; the second took 19.7 ms on CPU.
This used Python 3.12.7, FastEmbed 0.8.1 and ONNX Runtime 1.30.0, with model SHA256
`c623d0bcb99f4622beb413eaef00cfbe5db20df9f1dd982da4b4f26022881870`.
Network access was forbidden for the probe and the original model cache stayed
byte-identical. This is a functional smoke, not evidence of a general retrieval
quality gain from reranking.

An earlier ONNX Runtime 1.28.0 profiling run on the same model recorded 95 CUDA kernel
events and two CPU events, proving actual GPU node execution. Provider names
alone would not prove that. Separate CPU/CUDA embedding comparisons produced
finite vectors with minimum document cosine similarity 0.99999779 and identical
top-source results for five probe queries.

## AMD validation and boundaries

The local AMD Radeon integrated adapter was identified through DXGI vendor ID
`0x1002` at adapter index 1. Index 0 on this machine is NVIDIA; adapter indices
must not be assumed to identify a vendor on another machine.

An isolated Python 3.12 environment with ONNX Runtime DirectML 1.24.4 executed
the real model on AMD: profiling recorded 95 DirectML kernel events and two CPU
events. FastEmbed 0.8.0 then produced four finite 384-dimensional vectors with
CPU/DirectML cosine similarities from 0.9999959 to 0.9999974. The effective
session disabled memory patterns and used sequential execution, as required by
[ONNX Runtime's DirectML documentation](https://onnxruntime.ai/docs/execution-providers/DirectML-ExecutionProvider.html).

The integration uses explicit `gpu: "directml"` plus a validated `device_id`.
Automatic selection remains CUDA/CPU. DirectML requires serialized calls on a
session and a conservative default batch of eight. In the cold microtest AMD
was slower than CPU; no AMD speedup is claimed.

The application-level DirectML run passed all integrity checks and exited
successfully: 149 chunks from seven public documents, finite vectors, hybrid
queries in English and Portuguese, concurrent reads, edit/delete/force cycles,
FTS5 consistency and reopening the persisted database. Initial indexing took
21.534 seconds; sampled peak RSS was 452,055,040 bytes. This run used Python
3.12.7 and the same source-document hashes as the final CPU/CUDA runs, but a
different FastEmbed/ONNX Runtime distribution. It is a functional AMD validation,
not a controlled runtime-identical comparison against the CPU/CUDA table above.

A separate fresh CUDA 12 environment also passed application inference with
16 finite 384-dimensional embeddings: Python 3.12.7, FastEmbed 0.8.1, ONNX
Runtime GPU 1.26.0, CUDA runtime 12.9.79 and cuDNN 9.27.0.42. The installation
recipe removes both overlapping ONNX distributions and reinstalls only the
GPU distribution. FastEmbed and Chroma still declare the CPU distribution in
their package metadata, so `pip check` reports those two missing requirements.
The [GPU setup guide](gpu-setup.md) documents this upstream packaging limitation;
successful inference does not make that dependency metadata consistent.

Linux AMD and macOS GPU execution were not physically tested on this Windows
host. Platform behavior and CPU fallback require the project CI matrix in
addition to local tests. ROCm/MIGraphX support is not implied by Windows DirectML
support.

## Memory/storage measurements

Exploratory before/after measurements used the original implementations from
the audit base and identical local workloads:

| Workload | Before | After |
| --- | ---: | ---: |
| Python bytes retained after 100,001 metric observations | 3,201,024 | 328 |
| Metric exposition median, ten calls without active tracemalloc | 4.857 ms | 0.0036 ms |
| 100 FTS5 updates in a 100,000-row index | 1.754 s | 0.0618 s |
| Rows after replaying the same 100,000 chunk IDs | 200,000 | 100,000 |
| Initial 100,000-row insertion | 0.412 s | 0.800 s |
| BM25 retained Python memory, 10,000 documents / 1.99 million tokens | 120,711,243 B | 26,859,694 B |
| BM25 build time in that traced workload | 1.778 s | 1.788 s |

The indexed identity/upsert fix trades initial insertion cost for faster updates
and correct replay. Metrics retention is bounded per metric/label series, not
across an unlimited number of arbitrary series. These measurements are evidence
from one host and should not be presented as cross-platform benchmark promises.

BM25 uses a token pool owned by the index rather than retaining a separate string
for every repeated token. In this workload that reduced retained Python memory
by 77.75%, with about 0.6% more build time under active tracing. Clearing the
index released the pool; the measurement retained 1,665 bytes afterwards. The
pool is not global `sys.intern` state. Concurrent-search tests also verify that
a rebuild publishes a coherent scoring snapshot. Lazy initialization does not
wait on a long-running ingestion: it keeps the published BM25 snapshot, or
temporarily uses semantic retrieval when no snapshot has been loaded yet.

A pre-CI alternating cache probe used 18 rounds of 20,000 calls per implementation,
rotating the three variants in the same process with identical payloads. For
one result, the original shared-reference cache took 2.357 microseconds, generic
deepcopy took 3.588 microseconds and the then-current tuple-key/selective-copy cache
took 1.337 microseconds. With five results containing keyword lists, the values
were 2.181, 16.280 and 6.621 microseconds, respectively. The copy implementation
preserves aliases/cycles and isolates mutable containers; the original did not.
The five-result case therefore retains a correctness cost relative to shared
references, while improving on generic deepcopy by 59%. These are diagnostic
microbenchmarks, not a waiver of the unchanged 10% performance gate.

The first Linux CI run still reported a 27.6% hot-cache regression. The follow-up
classifies private snapshots at insertion: a list of distinct exact dictionaries
with exact immutable keys/values can use shallow row copies at lookup. Aliases,
cycles, subclasses and nested mutable values retain the general clone path.
This preserves invalidation generations and moves classification off the hot
path. A new 24-round / 20,000-call alternating probe measured 1.528 microseconds
for the original shared-reference cache, 1.062 for the pre-plan copy and 0.543
for the final plan on the one-result workload. The nested-payload path remained
within 3.45% of its prior timing; no benchmark or threshold was changed.

The complete benchmark suite passed its 23 functional assertions in each of
four isolated runs, ordered baseline/candidate/candidate/baseline. Paths and
source hashes confirmed that the baseline loaded the original implementation.
Both before/after timing comparisons still tripped the 10% gate on different
rows; neither failed result was discarded. An earlier attempted baseline had
loaded candidate modules through pytest's import path and was invalidated.

A diagnostic run then alternated each operation 24 times inside one process,
using independent runtime packages and restricting only the measurement process
to eight CPUs. Candidate median changes were +1.22% for small Markdown chunks,
+0.32% for 100 concurrent queries, +5.14% for the flagged FTS5 query and -1.00%
for reindex batches of 2,000. Large Markdown and nested JSON controls changed
by +1.28% and +0.36%; hot cache improved by 27%. This supports substantial
between-run variation on this host. It does not turn the failed local gate
runs into passes; the final PR CI verdict remains separate.

## Dependency audit

A clean editable QA environment resolved FastEmbed 0.8.1, CPU ONNX Runtime 1.30.0,
ChromaDB 1.5.9 and MCP 2.3.0. `pip check` passed. After upgrading the isolated
environment's pip, `pip-audit` still reported the four unique known ChromaDB
advisories already excepted by the repository's CI. The advisory feed duplicated
one entry, producing five rows. No upstream fixed version was listed at the time
of verification.

The [Chroma code-injection advisory](https://github.com/advisories/GHSA-f4j7-r4q5-qw2c)
describes its HTTP collection-management endpoint. This project uses an embedded
`PersistentClient`; it does not expose that Chroma HTTP API. This narrows the
applicability of that specific attack path but is not a claim that the dependency
is vulnerability-free. Do not expose a separate Chroma server under this audit's
validation claim.

The CI resolver's old pip 26.1.2 pin also predates a
[fixed package-index URL handling vulnerability](https://github.com/advisories/GHSA-qwm4-qh6w-59xr).
The resolver workflow now uses pip >=26.2 and exports the actual dependency
closure from pip's installation report. A clean resolution exported 108 pins;
the advisory was not added to the exception list.

## Final validation record

The final local integration run passed **1,122 tests**, with one existing
conditional documentation skip and five chaos tests excluded by the default
marker selection. Those five chaos tests passed in a separate explicit run.
Measured line coverage was **81.86%** on Windows / Python 3.12.7. No reruns were
enabled. Five warnings came from legacy Chroma mock embedding configuration in
deduplication fixtures. This run includes the final cache-generation fence,
OS process lock, optional-metadata and custom FTS5 path corrections, plus the
follow-up cache-copy plan and package-resource ignore regression.

CPU, CUDA and DirectML final E2E runs all passed, using the same public source
snapshot and isolated writable paths. The wheel built from the sdist imported
from outside the checkout and initialized all five presets plus config.example
with byte-identical source contents. Strict mypy passed for all 13 files in the
CI command; API checks passed against the unchanged baseline; Ruff lint/format,
version synchronization and the CHANGELOG gate passed. Bandit passed at the CI
HIGH severity / MEDIUM confidence threshold; docstring coverage was 89.8%
against the unchanged 80% requirement.

The first PR CI run exposed a source-checkout issue that the local wheel build
did not detect: the new multilingual bundle was hidden by `data/` in .gitignore.
The corrected ignore rules retain private runtime data exclusions and allow
package resources to be versioned normally. A regression uses a temporary Git
repository, and a tracked-only Git archive proves that initialization exports
all five presets without relying on ignored local files.

Cross-platform acceptance is determined by the pull request's nine Linux,
macOS and Windows / Python 3.11–3.13 jobs, not inferred from this Windows host.
The local benchmark gate caveat above remains part of the validation record.
The production installation, document corpus and GPU drivers were not changed.
